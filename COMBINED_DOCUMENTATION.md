# 📚 Полная документация системы расчета логистических ставок

## 1. Введение

### 1.1. О проекте
Система предназначена для автоматизации расчета стоимости логистических перевозок с поддержкой различных типов транспорта:
- **Морские перевозки** (прямые и комплексные)
- **Железнодорожные перевозки** (прямые и комплексные)
- **Комплексные перевозки** (море + железная дорога)

### 1.2. Роли пользователей
- **Администратор** – полный доступ ко всем функциям, управление пользователями, настройка системы.
- **Менеджер по закупкам** – загрузка и обновление ставок, управление тарифами, работа с базами данных.
- **Менеджер по продажам** – расчет стоимости перевозок, поиск оптимальных маршрутов, работа с клиентами.

### 1.3. Быстрый старт
**Предварительные требования:**
- Node.js 16+
- PostgreSQL 12+
- Созданная база данных PostgreSQL

**Настройка базы данных:**
1. Создайте базу данных PostgreSQL.
2. Настройте переменные окружения в файле `.env`:
   ```bash
   DATABASE_URL=postgresql://username:password@localhost:5432/database_name
   JWT_SECRET=your-secret-key-change-in-production
   ```

**Установка зависимостей:**
```bash
npm install
```

**Запуск сервера:**
```bash
npm start
```

**Доступ к приложению:**  
Откройте в браузере: `http://localhost:3000`

**Данные для входа по умолчанию:**
- Логин: `admin@logistics.com`
- Пароль: `admin123`

### 1.4. Статус миграции интерфейса (важно)
- В проекте запускается новый SPA на **React + TypeScript** (папка `app/`).
- Старые HTML/JS страницы и модули **оставлены для тестирования и сравнения**.
- После приемки и полного тестирования запланирована **тотальная чистка**: удаление legacy‑файлов и старых связей.

## 6. Техническая документация

### 6.1. Архитектура приложения
Приложение представляет собой SPA (Single Page Application) на Node.js с серверной частью на PostgreSQL и **новой клиентской частью на React + TypeScript**. В репозитории временно сохраняется legacy‑интерфейс на чистом JavaScript для сравнения и тестирования, после завершения миграции он будет удалён.

**Серверная часть:**
- Node.js + Express – сервер для обслуживания статических файлов и API
- PostgreSQL + Sequelize ORM – реляционная база данных для хранения всех данных
- JWT аутентификация – безопасная система авторизации
- Helmet – настройки безопасности заголовков
- Compression – сжатие данных Gzip
- Content Security Policy – политика безопасности контента

**Клиентская часть:**
- React + TypeScript (Vite) – основной фронтенд
- HTML/CSS/JavaScript – legacy фронтенд (временно, будет удалён после тестирования)
- SheetJS (XLSX) – обработка Excel файлов
- localStorage – хранение сессий и резервных копий
- Fetch API – взаимодействие с серверными API
- JWT токены – авторизованные запросы к серверу

### 6.2. Типы перевозок
1. **Море** – морские контейнерные перевозки
2. **ЖД** – железнодорожные перевозки
3. **Прямое ЖД** – прямые железнодорожные перевозки
4. **Прямое море** – прямые морские перевозки
5. **Море+ЖД** – комбинированные перевозки (комплексные расчеты)

### 6.3. Логика обработки морских перевозок (раздельное море - море не прямое)

Система использует улучшенную логику обработки морских перевозок с поддержкой поля "Город" (City) и каскадной фильтрацией:

#### Архитектура поискового движка
- **EnhancedSeaSearchEngine** – класс для каскадной фильтрации морских ставок
- **Кеширование результатов** – для повышения производительности
- **Нормализация названий** – регистронезависимый поиск с обработкой специальных символов

#### Каскадная фильтрация полей
1. **POL (Port of Loading)** – список портов отправления с ненулевыми ставками
2. **Город (City)** – динамически фильтруется на основе выбранного POL (только города с ненулевыми ставками)
3. **POD (Port of Discharge)** – динамически фильтруется на основе POL и City
4. **DROP OFF AREA** – динамически фильтруется на основе POL, City и POD
5. **Тип контейнера** – показывается только после выбора всех предыдущих полей

#### Особенности реализации
- **Фильтрация по ненулевым ставкам** – в выпадающих списках отображаются только значения, для которых есть ставки > 0
- **Частичные совпадения** – поддержка частичного совпадения названий портов и городов
- **Автоматическая очистка зависимых полей** – при изменении вышестоящего поля очищаются все зависимые поля
- **Сохранение фокуса** – при обновлении интерфейса сохраняется фокус на текущем поле ввода

#### Техническая реализация
- **Модуль:** [`modules/sea.js`](modules/sea.js:1)
- **Основной класс:** `EnhancedSeaSearchEngine`
- **Функция инициализации:** `setupEnhancedSeaChainUpdate(data)`
- **Интеграция с интерфейсом продаж:** через `SeaModule.setupEnhancedSeaChainUpdate(data)` в [`scripts/sales-script.js`](scripts/sales-script.js:522)

#### Формат данных морских перевозок
Каждая запись морских перевозок содержит следующие поля:
- `pol` – порт отправления (Port of Loading)
- `city` – город (добавлено в новой версии)
- `pod` – порт назначения (Port of Discharge)
- `dropOffArea` – зона выгрузки
- `soc20`, `soc40`, `dc20`, `hc40` – ставки для разных типов контейнеров
- `carrier` – перевозчик
- `agent` – агент
- `dateOfValidity` – дата действия ставки
- `etd` – Estimated Time of Departure
- `remarks` – примечания

#### Пример использования в интерфейсе менеджера по продажам
1. Пользователь выбирает тип расчета "Раздельные ставки" → "Море"
2. Система загружает данные морских перевозок из базы данных
3. В поле POL отображаются только порты с ненулевыми ставками
4. При выборе POL автоматически фильтруются доступные города
5. При выборе города фильтруются доступные POD
6. При выборе POD фильтруются доступные Drop Off Areas
7. После выбора всех полей становятся доступны типы контейнеров
8. При выборе типа контейнера отображаются соответствующие ставки

## 7. Архитектура комплексных расчетов

### 7.1. Объяснение сообщения в логах
Сообщение в логах сервера:
```
⚠️ Тип данных "complex" не загружается из базы данных (комплексный расчет)
```
**Это нормальное поведение системы, а не ошибка!**

### 7.2. Почему это происходит
Система использует гибридный подход к хранению данных:

**Типы данных, хранящиеся в PostgreSQL:**
- `sea` – морские перевозки
- `rail` – железнодорожные перевозки
- `direct_rail` – прямые железнодорожные перевозки
- `direct_sea` – прямые морские перевозки
- `tariff` – тарифы и дополнительные услуги

**Тип данных, НЕ хранящийся в PostgreSQL:**
- `complex` – комплексные расчеты (море + железная дорога)

### 7.3. Как работают комплексные расчеты
Комплексные расчеты выполняются динамически на основе данных из других типов:
1. **Сбор данных** из таблиц `sea`, `rail`, `direct_sea`, `direct_rail`
2. **Автоматическое соединение** маршрутов по городам и портам
3. **Конвертация валют** – морские ставки в USD конвертируются в RUB
4. **Сложение ставок** – морская часть + железнодорожная часть
5. **Добавление ВТТ** – при включении триггера ВТТ

**Фильтр "Куда" в комплексных ставках:**
- **Море (sea)** – сравнение по `DROP OFF AREA VIA VVO`, если заполнено, иначе по `POD`
- **Прямое море (direct_sea)** – сравнение по `POD`
- **ЖД (rail)** – сравнение по `destination`
- **Прямое ЖД (direct_rail)** – сравнение по `arrivalCity`

### 7.4. Преимущества такого подхода
- **Экономия места в базе данных** – комплексные ставки не дублируют данные
- **Гибкость соединений** – автоматическое нахождение всех возможных комбинаций
- **Актуальность данных** – изменения в отдельных ставках автоматически отражаются в комплексных расчетах
- **Производительность** – отсутствие необходимости в сложных JOIN операциях

### 7.5. API обработка
- **Запрос**: `GET /api/data/complex`
- **Ответ**: `{ data: [], lastUpdate: null, count: 0 }`
- **Сообщение**: Информационное предупреждение в логах

### 7.6. Клиентская обработка
- **Функция**: `Utils.showLastUpdate('complex', 'last-update')`
- **Действие**: Показывает текст "Комплексный расчет (данные не сохраняются)"
- **Расчет**: Выполняется динамически в функции `calculateAllRates()`

## 9. Система фильтрации для менеджера по продажам (январь 2026)

### 9.1. Обзор системы фильтрации
Система фильтрации была разработана для менеджера по продажам в интерфейсе комплексных ставок. Фильтры позволяют сужать результаты расчетов по трем ключевым параметрам:
- **Линия (перевозчик)** – фильтрация по морским перевозчикам
- **Агент** – фильтрация по агентам морских перевозок
- **Терминал ЖД** – фильтрация по агентам железнодорожных перевозок

### 9.2. Архитектура фильтрации
Система использует Excel-подобный подход к фильтрации с поддержкой множественного выбора, поиска и удобного интерфейса.

#### Ключевые компоненты:
1. **Excel-подобные фильтры** – выпадающие списки с чекбоксами и поиском
2. **Динамическая загрузка данных** – значения фильтров загружаются из соответствующих баз данных
3. **Множественный выбор** – возможность выбора нескольких значений одновременно
4. **Поиск по значениям** – фильтрация опций внутри выпадающего списка
5. **Верхнее открытие** – выпадающие списки открываются вверх для экономии экранного пространства

### 9.3. Источники данных для фильтров
Система использует различные источники данных для каждого типа фильтра:

#### 1. Линия (перевозчик)
- **Источник:** Базы данных `sea` и `direct_sea`
- **Поля:** `carrier`, `line`, `shippingLine`, `vessel`
- **Логика:** Собирает все уникальные значения из полей, связанных с перевозчиком

#### 2. Агент
- **Источник:** Базы данных `sea` и `direct_sea`
- **Поля:** `agent`, `forwarder`, `shippingAgent`
- **Логика:** Собирает все уникальные значения из полей, связанных с агентом

#### 3. Терминал ЖД
- **Источник:** База данных `rail` (только обычное ЖД, не прямое)
- **Поле:** `agent`
- **Логика:** Собирает только поле `agent` из базы данных железнодорожных перевозок
